# RF-0002 — Policy-First Admissible Routing for Knowledge and Compute

**Identifier:** RF-0002  
**Status:** EXPERIMENTAL  
**Version:** 0.2  
**Disclosure date:** 2026-09-05  
**Author:** Marcelo Roldão Matos

## Purpose

This disclosure records the Resolutive routing layer that selects where a request should be resolved or processed across heterogeneous nodes while enforcing privacy/policy admissibility before optimizing efficiency.

## Core questions

The router separates two questions:

1. Which node is likely to know or resolve the request?
2. Which admissible node can process it most efficiently now?

The architecture therefore routes over both knowledge state and compute capability rather than treating all nodes as equivalent endpoints.

## Inputs

Candidate inputs include knowledge availability, resolver/model capability, CPU/GPU/NPU class, RAM/VRAM, load, latency/network distance, privacy scope, organization policy, reputation, contribution/consumption credits, energy and cost policy.

## Policy-first rule

```text
candidates = discover(request)
admissible = filter_by_scope_identity_policy(candidates)
ranked = score(admissible, knowledge, capability, load, latency, cost, reputation, credits)
return best(ranked) or explicit fallback
```

A lower-cost or faster node cannot override privacy or authorization restrictions.

## Architectural boundary

```text
Memoria.ia         -> memory/state semantics
MA2A / M2A2        -> identity, federation, authorized exchange
resolutive-routing -> admissibility and route selection over knowledge/compute state
```

## Prior-art narrowing

External prior-art review found substantial antecedents for policy-first routing, access-control filtering, heterogeneous compute scheduling, capability routing, latency/cost optimization, reputation and resource accounting. These components are not claimed individually.

The narrower Resolutive organization is the explicit routing boundary over both **knowledge/memory availability** and **heterogeneous compute state**, after admissibility filtering, within the Memoria.ia/MA2A architecture.

This disclosure is therefore retained primarily as an architectural integration record; it is not currently treated as the strongest novelty candidate in the family.

## Scope and limitations

Performance claims require measured multi-node experiments against static-routing and broadcast baselines. The existence of a prototype and DOI does not establish novelty or superiority over prior systems.

Status remains `EXPERIMENTAL`; the archived v0.1.0 prototype is evidence of implementation and publication, while broader performance/novelty claims remain open.
