# RF-0002 — Policy-First Admissible Routing for Knowledge and Compute

**Identifier:** RF-0002  
**Status:** EXPERIMENTAL  
**Version:** 0.1  
**Disclosure date:** 2026-09-05  
**Author:** Marcelo Roldão Matos

## Purpose

This disclosure records the Resolutive routing layer that selects where a request should be resolved or processed across heterogeneous nodes while enforcing privacy/policy admissibility before optimizing efficiency.

## Core questions

The router separates two questions:

1. Which node is likely to know or resolve the request?
2. Which admissible node can process it most efficiently now?

The architecture therefore routes over both knowledge state and compute capability rather than treating all nodes as equivalent endpoints.

## Inputs

Candidate routing inputs include:

- local/organizational/public knowledge availability;
- model or resolver capability;
- CPU/GPU/NPU class;
- available RAM/VRAM;
- load and expected throughput;
- latency/network distance;
- privacy scope and organization policy;
- node reputation;
- compute/storage/knowledge credit balances;
- energy and cost policy.

## Policy-first rule

Admissibility precedes optimization:

```text
candidates = discover(request)
admissible = filter_by_scope_identity_policy(candidates)
ranked = score(admissible, knowledge, capability, load, latency, cost, reputation, credits)
return best(ranked) or explicit fallback
```

A lower-cost or faster node cannot override a privacy or authorization restriction.

Suggested scopes include `PUBLIC`, `ORGANIZATION`, `PRIVATE`, and `LOCAL_ONLY`.

## Avoiding broadcast

When useful knowledge-density or capability information is available, the router should prefer targeted candidate selection instead of global flooding. Public/authorized knowledge requests may use an ECHO-style primitive routed toward promising nodes.

## Resource reciprocity

The routing architecture may maintain auditable, non-financial internal ledgers such as:

```text
compute_credit
storage_credit
knowledge_credit
```

These balances represent measurable contribution/consumption and are not defined as cryptocurrency or direct equivalents of model tokens.

## Architectural boundary

```text
Memoria.ia        -> memory/state semantics
MA2A / M2A2       -> identity, federation, authorized exchange
resolutive-routing -> selects the best admissible knowledge/compute route
```

The routing layer does not own the memory database and does not replace MA2A identity/security.

## Evidence baseline

Public implementation repository: `marceloroldao/resolutive-routing`.

The v0.1 prototype includes typed node/request contracts, policy-first deterministic routing, explainable decisions, explicit fallback, separated compute/storage/knowledge accounting, routing baselines, a deterministic multi-node simulator, tests and a reproducible microbenchmark.

Archival DOI: `10.5281/zenodo.22235924`.

## Scope and limitations

This disclosure does not claim invention of load balancing, schedulers, capability routing, reputation systems, access control, accounting ledgers, or distributed compute individually. The disclosed organization is the use of policy-first admissibility combined with memory/knowledge availability and heterogeneous compute-state routing within the Resolutive/MA2A architecture.

Performance claims require measured multi-node experiments against static routing and broadcast baselines.
