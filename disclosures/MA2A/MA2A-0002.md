## 1. Technical problem

When multiple agents or edge devices update related memory state, the network must determine whether updates are compatible, stale, concurrent, unauthorized, or conflicting. Natural-language reconciliation is non-deterministic and expensive. MA2A-0002 discloses a synchronization model based on versioned trajectory deltas and deterministic conflict handling.

## 2. State model

Each synchronizable trajectory record is represented by a stable address and version metadata:

```text
TrajectoryRecord {
    trajectory_address
    version
    state_digest
    scope
    owner_or_org
    payload_or_reference
}
```

A proposed update is represented by:

```text
Delta {
    trajectory_address
    base_version
    new_version
    operation
    state_digest_before
    state_digest_after
    scope
    logical_clock_or_sequence
    sender_id
    signature
}
```

## 3. Deterministic acceptance rule

For a local authoritative record `R` and incoming delta `D`:

```text
if not authorized(D): REJECT
if not integrity_ok(D): REJECT
if D.scope violates boundary: REJECT
if D.base_version == R.version:
    APPLY(D)
else:
    CONFLICT(R, D)
```

The basic fast path is therefore version equality plus policy and integrity checks. Conflict handling must itself be deterministic and versioned.

## 4. Conflict classes

The protocol distinguishes at least:

1. **Stale update** — incoming `base_version < current_version` and update depends on obsolete state.
2. **Duplicate/replay** — already applied delta or repeated sequence/nonce.
3. **Concurrent update** — two accepted-origin deltas share the same base version but diverge.
4. **Scope conflict** — update attempts to broaden replication/privacy beyond authorization.
5. **Semantic conflict** — two technically valid states cannot both satisfy the application invariant.

## 5. Conflict strategies

The protocol permits deterministic strategies identified by a policy/version ID, for example:

- reject-loser and rebase;
- monotonic field merge;
- deterministic last-writer by logical order only where safe;
- authority-priority merge;
- application-specific resolutive transition;
- immutable branch creation followed by later explicit reconciliation.

A compliant implementation must not silently use non-deterministic LLM judgment as the consensus rule. An LLM may propose a resolution at L1, but the committed state transition must be represented as an explicit deterministic delta subject to policy.

## 6. Synchronization procedure

```text
SYNC(local_summary, remote_summary):
    compare known trajectory addresses and versions
    request only missing/divergent deltas
    for each delta in deterministic order:
        validate identity, scope, integrity, sequence
        if base version matches:
            apply
        else:
            invoke conflict policy
    emit resulting state digest/version
```

The protocol is delta-oriented: unchanged trajectories need not be retransmitted in full.

## 7. Offline operation

L1 may continue generating local deltas while disconnected. On reconnection, the peer submits a chain or compact set of pending updates. The receiving authority validates the base-version relationships and either applies the chain or identifies the earliest conflict.

This supports local-first operation without asserting that all concurrent offline edits can be automatically merged.

## 8. Integrity and convergence

After applying an accepted sequence of deltas, peers can compare a deterministic digest of the resulting trajectory state. Matching digest plus matching version provides a compact convergence check for that record.

A digest mismatch must trigger repair/retransmission or quarantine; it must not be hidden by merely advancing version metadata.

## 9. Privacy

Synchronization eligibility is constrained by the scope model in MA2A-0001. `private` data is not made globally synchronizable merely because a delta exists. Scope changes are explicit state transitions requiring appropriate authority.

## 10. Worked example

Device A and Device B both hold trajectory `t7` at version 12. A creates delta `D_A: 12 -> 13`. B independently creates `D_B: 12 -> 13` while offline.

When A's delta reaches the organization authority first, the authoritative state becomes 13. When B later submits a delta based on version 12, it is classified as concurrent/stale relative to current state rather than blindly overwriting it. The configured conflict policy may reject B for rebase, create a branch, or deterministically merge if the operation type permits it.

## 11. Complexity boundaries

Known-address version lookup may use O(1)-average indexed access. However, synchronization cost depends on the number of deltas, cryptographic verification, persistence, conflict policy, and network transport. This disclosure does not claim O(1) cost for arbitrary reconciliation.

## 12. Failure modes

- malicious or corrupted delta chains;
- logical clock manipulation;
- split authority;
- conflicting policy versions;
- non-commutative updates presented as mergeable;
- lost intermediate deltas;
- rollback/replay;
- inconsistent scope enforcement.

## 13. Relation to existing distributed-systems techniques

Relevant comparison classes include optimistic concurrency control, MVCC, event sourcing, Lamport/vector clocks, CRDTs, replicated state machines, anti-entropy synchronization, and append-only logs. MA2A does not claim to replace these principles wholesale; it specifies how deterministic versioned synchronization is attached to resolutive trajectory addresses and privacy/identity boundaries.
