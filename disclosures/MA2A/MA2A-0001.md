## 1. Technical problem

Multi-agent AI systems commonly exchange natural-language messages or verbose structured prompts through APIs. This couples inter-agent synchronization to tokenization, model context windows, inference cost, latency, and possible propagation of generated errors.

MA2A-0001 discloses an architecture in which cooperating agents synchronize deterministic memory/trajectory state rather than requiring natural-language LLM-to-LLM transport for every interaction. Language models, when used, remain edge-side interpretation/generation components and are not required in the central synchronization plane.

## 2. Definitions and assumptions

- **MA2A:** Memoria.ia Agent-to-Agent protocol family.
- **L1 — Edge/Client:** user/device boundary containing local memory, optional local LLM, sensors, UI/rendering, and private state.
- **L2 — Mesh/Transport:** peer connectivity layer, including direct local links or authenticated network tunnels.
- **L3 — Central Coordination:** lightweight routing, synchronization, validation, and persistence service. It does not require an LLM for protocol operation.
- **Trajectory delta:** compact state change referencing a resolutive address/trajectory and its mutation/version information.
- **Scope:** privacy/replication class attached to state, e.g. `private`, `user`, `shared`, `global`.
- **Organization root:** a company's central Memoria.ia authority through which its licensed devices/agents are organized.

## 3. Technical solution

MA2A separates cognition from synchronization.

```text
                    selected state/deltas
+----------------+       MA2A        +-------------------+
| L1 Device A    | <----------------> |                   |
| local memory   |                    | L3 Coordination   |
| optional LLM   |                    | route / validate  |
+----------------+                    | persist / relay    |
        ^                             | NO required LLM   |
        | L2 peer/mesh                +-------------------+
        v                                      ^
+----------------+                             |
| L1 Device B    | ----------------------------+
| local memory   |       selected state/deltas
| optional LLM   |
+----------------+
```

The core architectural rule is:

`LLM semantics stay at L1; protocol state synchronization is deterministic and may traverse L2/L3 without transporting LLM prompts.`

L3 therefore acts as a coordination plane rather than a centralized inference service. A single organization's devices may first converge on an organizational Memoria.ia authority, while that authority participates in the licensed wider network according to policy.

## 4. Disclosed technical features

1. Three-layer separation of edge cognition, transport/mesh, and central coordination.
2. Optional LLM execution restricted to edge/client operation for the protocol's core path.
3. State/trajectory delta transport instead of mandatory natural-language agent messages.
4. Local-first behavior: L1 continues to operate on local memory when disconnected, subject to application rules.
5. Explicit privacy scopes determining which trajectories are eligible for synchronization.
6. Central L3 can reject local/private state from global ingestion.
7. Hierarchical organization model: devices can bind to a company's central Memoria.ia identity rather than each device independently acting as a licensed network organization.
8. Protocol architecture designed to support deterministic conflict handling and cryptographic identity in subsequent MA2A disclosures.

## 5. Protocol state model

A minimal synchronization envelope can be represented as:

```text
Delta {
    protocol_version
    sender_id
    organization_id
    trajectory_address
    base_version
    new_version
    operation
    scope
    payload_or_reference
    integrity_digest
    timestamp_or_logical_clock
    signature
}
```

Normative high-level processing:

```text
L1_CREATE_DELTA(change):
    delta := encode(change)
    delta.scope := classify(change)
    sign(delta)
    if delta.scope in {private, user}:
        retain locally unless an explicit policy permits organizational sync
    else:
        transmit through authorized L2/L3 path

L3_INGEST(delta):
    authenticate sender and organization
    verify signature and integrity
    verify protocol version and replay constraints
    enforce scope policy
    if scope is not eligible for L3:
        reject
    resolve trajectory address
    validate base/new version relation
    apply or invoke deterministic conflict rule
    persist accepted state
    relay only to authorized subscribers
```

This disclosure defines architecture, not the final binary wire encoding. A later MA2A document may freeze CBOR/MessagePack/Protobuf/custom binary encoding after benchmarking.

## 6. Session and organization hierarchy

The intended organizational topology is:

```text
Official network root / trust policy
            |
      Organization A
      central Memoria.ia
       /      |       \
    phone    robot    IoT
     L1       L1      L1
```

The organization has a stable cryptographic identity. Individual devices receive subordinate identities/credentials and communicate through or under that organizational authority. This reduces licensing and policy management from “one commercial identity per device” to “one organization identity with controlled device membership.”

The precise certificate and handshake mechanism is reserved for MA2A-0003.

## 7. Privacy boundary

The protocol must distinguish storage locality from network reachability. At minimum:

- `private`: never leaves the originating device by default;
- `user`: may synchronize only inside the user's authorized domain;
- `shared`: may be replicated to explicitly authorized peers/organization services;
- `global`: eligible for wider network publication/replication subject to trust and validation rules.

L3 must not silently upgrade a scope. A transition from narrower to broader scope requires an authorized policy decision at the appropriate boundary.

## 8. Worked example

A robot and a phone belong to the same company/user domain. The robot learns a non-sensitive operational trajectory and classifies it as `shared`. It sends a signed delta referencing the trajectory address rather than composing a natural-language explanation. The organizational Memoria.ia validates and stores the delta. The phone later synchronizes that trajectory state and can locally render or explain it using its own optional LLM.

If the robot marks a trajectory `private`, the L3 ingestion path rejects or never receives it according to the deployment policy.

## 9. Performance claims and measurement boundaries

MA2A is designed to reduce token transport overhead between cooperating resolutive agents. “Zero token transport overhead” means the protocol itself does not require LLM token strings for deterministic state synchronization; it does **not** mean zero bytes on the network.

Likewise, sub-millisecond or O(1) claims must be attached to specific local route-resolution operations and demonstrated by benchmarks. End-to-end synchronization includes serialization, cryptography, network latency, persistence, and conflict resolution and therefore is not asserted to be universally O(1) or sub-millisecond.

## 10. Security and failure modes

The architecture requires defenses against:

- unauthorized organizations/devices;
- forged deltas and identity substitution;
- replay and stale-version attacks;
- unauthorized scope escalation;
- malformed/corrupted state;
- split-brain/offline concurrent updates;
- compromised organizational authority;
- leakage through metadata even when payload is private.

Cryptographic handshake, certificate lifecycle, revocation, and official-network admission are specified separately in MA2A-0003.

## 11. Limitations and unresolved questions

This revision does not freeze:

- final transport encoding;
- discovery mechanism;
- deterministic conflict-resolution algorithm;
- PKI certificate schema and revocation mechanism;
- bandwidth/latency benchmarks;
- production multi-tenant isolation;
- exact mapping between organizational and user-level authorities.

It also does not claim interoperability with unrelated A2A protocols unless an explicit gateway is specified.

## 12. Related work and distinction

Relevant comparison classes include distributed state replication, CRDTs, event sourcing, pub/sub systems, content-addressed networks, service meshes, PKI-based device fleets, and natural-language agent-to-agent protocols. MA2A's disclosed architectural distinction is the combination of resolutive trajectory-address synchronization, edge-local optional LLM semantics, explicit privacy scopes, and a non-LLM central coordination plane.

A formal prior-art survey and interoperability comparison remain required before VALIDATED status.
